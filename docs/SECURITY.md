# Local creations and preview security

## Trust boundaries

Repository-owned calendar HTML, JavaScript and approved mission copy are trusted. Every imported file is untrusted, even when generated by AI. The stored file is never injected into the calendar DOM, evaluated by the parent, uploaded or committed to GitHub.

`preview.js` parses a separate inert document, prepends a restrictive CSP, removes refresh/base/prefetch hints, serialises it and assigns it to a newly created iframe's `srcdoc`. The original stored HTML stays unchanged for export.

The iframe uses **`sandbox="allow-scripts allow-forms"`**. It never receives `allow-same-origin`, top-navigation, popups, downloads, storage-access or escape permissions. This produces an opaque origin, preventing access to the calendar DOM, cookies, localStorage and IndexedDB. Form handlers can run locally; `form-action 'none'` prevents actual submissions.

The parent CSP uses `frame-src 'none'`: inline `srcdoc` can run, while navigations of the child to URL-loaded documents are restricted. The preview's own CSP blocks connections, external scripts, external images, nested frames, objects, workers, manifests, external fonts and form destinations. Only inline scripts/styles and embedded data/blob visual/audio assets are allowed. Browser features such as camera, microphone, location, clipboard, sensors, payment and fullscreen are denied by the iframe's permission policy. Expansion is parent-controlled CSS, not an unsandboxed new tab.

The preview monitor posts only `ready` or `limited` status messages. The parent checks the source frame, opaque origin, preview session and message type, then updates explanatory text only. No received message can save or delete files, change stars, set names or execute code. Untrusted code could forge a status message within its own frame; it gains no authority by doing so.

## File handling

Only files with a `.html` extension, nonempty content, at most 10 MB, HTML root tags and no NUL bytes are accepted. This is usability validation, **not** a claim to sanitise executable code. The sandbox remains mandatory. MIME type alone is not trusted, because browsers and iOS Files may supply an empty or generic type.

IndexedDB writes resolve on transaction completion, not request success alone. Replacement is one transaction. A failed validation or save retains the prior record. Deletion requires a separate confirmation dialog, deletes the mission's local record only and never touches completion state. Export creates a temporary Blob URL from the exact stored content.

Production/test use different IndexedDB databases and star/name keys. The service worker caches app assets only, never imported HTML. Production packaging uses an allowlist. Neither the unlocked test build nor fixtures are in the Pages artifact.

## Known limits

- This is a browser sandbox, not a separate operating-system process or malware-analysis service. A CPU-hogging or memory-hogging creation can make a browser tab unresponsive.
- Platform policies and bugs differ. Physical Safari/iOS and Android tests remain required before claiming universal behaviour.
- CSP and sandbox limitations may prevent a perfectly ordinary project from fully running. The UI explains this rather than widening permissions.
- The app does not inspect, grade or guarantee the safety/correctness of a creation. Keep original files and test advanced features in an appropriate trusted environment.
- The calendar itself adds no tracking, analytics or collection. A static host may maintain its ordinary infrastructure logs. No child's name or imported-file content is sent by this app.
- Public source contains all mission copy. Date locks can be bypassed by changing the device clock and are intended for family use.

## Reporting a problem

Do not publicly attach a child's files, names or private data to an issue. Describe the browser, steps and a minimal synthetic reproduction. Keep `allow-same-origin` absent even if adding it appears to fix a preview feature.
